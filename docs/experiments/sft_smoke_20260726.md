# Column-rename tool SFT smoke — 2026-07-26

## Outcome

The first real Qwen2.5-Coder-7B tool-SFT run completed end to end on two
RTX 3090 GPUs. This validates the processed trajectory format, VERL
`MultiTurnSFTDataset`, LoRA/FSDP training, validation, checkpointing, and PEFT
adapter export. It is an integration smoke test, not a quality claim.

## Inputs and configuration

- Base model: local `Qwen2.5-Coder-7B-Instruct`
- Data: 74 train and 26 validation trajectories
- Split: by `db_id`; 38 train and 10 validation databases; no overlap
- Oracle trajectory: inspect version, inspect schema diff, observe stale-query
  failure, execute the repaired query, submit
- Method: LoRA rank 32, alpha 32, all linear layers
- Training: 5 steps, learning rate `2e-5`, max sequence length 4096
- Hardware: GPUs 0 and 3, distributed FSDP

## Observed result

| Metric | Value |
|---|---:|
| Train loss, steps 1–5 | 1.2699, 1.2703, 1.2169, 1.2224, 1.3451 |
| Validation loss | 1.1917 |
| Peak allocated memory / GPU | 22.47 GiB |
| Peak reserved memory / GPU | 23.24 GiB |
| Exported LoRA tensors | 392 |
| Portable adapter size | 309 MiB |

Every exported adapter tensor is nonzero. The adapter loads through PEFT with
rank 32, alpha 32, and targets `q_proj`, `k_proj`, `v_proj`, `o_proj`,
`gate_proj`, `up_proj`, and `down_proj`.

## Checkpoint note

This first run inherited VERL's FP32 checkpoint default and explicitly saved
both FSDP shards and a full HF-formatted PEFT state, producing a 59 GiB
checkpoint. After the portable adapter was extracted, loaded through PEFT,
checked for nonzero tensors, and checksummed, the redundant full-model,
optimizer, and FSDP files were removed. The training script now uses BF16 and
LoRA-only model shards by default, so subsequent smoke checkpoints should be
hundreds of MiB rather than tens of GiB.

The portable warm-start adapter is:

```text
checkpoints/sft_column_rename_smoke_2gpu/global_step_5/lora_adapter
```
